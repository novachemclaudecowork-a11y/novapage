加上 TWNIC 自動帶入的兩筆 NS（`ns11` / `ns12.twnic.net.tw`）。

### mailfilter 的身分已查明

第 6 筆的 `include:hibox.hinet.net` 指出郵件服務是 **中華電信 HiBox 企業郵件**。
第 3、4、5、6、7 筆全是同一套 HiBox 的組成：

```
外部寄信 → MX → mailfilter（過濾垃圾信）→ mail（郵件主機）
                                              ↑
                        員工收信：郵件軟體連 mail，或瀏覽器開 webmail
公司寄信 → 經 hibox.hinet.net 送出 → 收件方查 SPF（第 6 筆）確認是本人
```

**也就是說，公司確實有 `@novananoinks.com.tw` 的信箱在運作。**
七筆紀錄裡有五筆是郵件用的，搬家時全部都要原封不動帶走。

## 搬到 Cloudflare 的對照表

照這張表逐筆建立。**「代理狀態」那一欄填錯會讓信件全斷，務必確認。**

| 類型 | 名稱 | 內容 | 代理狀態 |
| --- | --- | --- | --- |
| A | `novananoinks.com.tw`（或填 `@`） | `45.77.23.226` | **灰色 DNS only** |
| A | `www` | `45.77.23.226` | **灰色 DNS only** |
| A | `mail` | `202.39.131.130` | **灰色 DNS only** |
| A | `mailfilter` | `210.71.187.212` | **灰色 DNS only** |
| CNAME | `webmail` | `mail.novananoinks.com.tw` | **灰色 DNS only** |
| TXT | `novananoinks.com.tw`（或 `@`） | `v=spf1 include:hibox.hinet.net ~all` | 不適用 |
| MX | `novananoinks.com.tw`（或 `@`） | `mailfilter.novananoinks.com.tw`，Priority **5** | 不適用 |

> ⚠️ **橘色雲朵（Proxied）只處理網頁流量，不處理郵件。**
> `mail`、`mailfilter`、`webmail` 任何一筆開成橘色，信件立刻全斷。
> 這是搬家最常見的致命錯誤，建立完務必再檢查一次這三筆。

> 💡 網站那兩筆（`@` 與 `www`）這個階段也先設灰色，
> 讓網站的行為與現在完全一致。等到真的要切換新站時再處理。

### 漏掉任何一筆會發生什麼

| 漏掉 | 後果 |
| --- | --- |
| MX 或 A `mailfilter` | **收不到信** |
| A `mail` | 員工的郵件軟體（Outlook 等）連不上，**收發都中斷** |
| CNAME `webmail` | 網頁版信箱打不開 |
| TXT（SPF） | **公司寄出去的信開始被判定為垃圾信** |

## 切換步驟

1. TWNIC → **DNS設定/代管**，把上方的 **「主機模式（TWNIC 代管）」切成「DNS 模式（自行管理）」**
2. 填入 `cass.ns.cloudflare.com` 與 `kellen.ns.cloudflare.com`，儲存
3. 等生效。Cloudflare 的狀態會從 **Pending** 變成 **Active**，通常數小時，最長 48 小時，生效時會寄信通知

### 切換後要驗的五件事

- [ ] `www.novananoinks.com.tw` 打得開，內容與以前相同

就照存檔的截圖重新打一次——**所以那張截圖在確認一切正常之前都不能弄丟**。

### Vultr 那台主機是設計公司租的，這有兩個意思

**好的一面**：不是公司的開銷，新站上線後不必處理退租，那台跟公司無關。

設計公司若停止續租或片面關機，現行網站隨時會消失，公司無從阻止。

這不是要急著搬，而是：**新站已經做好了，那就是這件事的保險。**
真的斷線時，把 DNS 指過來即可，不必在壓力下趕工。

## 怎麼把風險降到最低

會緊張是合理的，但這件事的風險比直覺上小。幾個事實：

**一、建好不等於生效。**
在 Cloudflare 把七筆紀錄全部建好之後，**什麼都不會發生**。
要等名稱伺服器改掉才生效。所以可以今天建好、慢慢核對、下個月再切換，
中間毫無壓力，也沒有任何期限。

**二、紀錄的值完全不變。**
不是重新設定郵件，只是把同樣七行字抄到另一個地方。
HiBox 那端完全不知道也不受影響。

**三、改錯可以改回來。**
名稱伺服器隨時能改回 `ns11/ns12.twnic.net.tw`。
TWNIC 的紀錄只要不刪，改回去就全部復原。

**四、信件出問題通常是「延遲」，不是「遺失」。**
若 MX 查不到或連不上，寄件方的伺服器會**自動重試**，一般持續 48～72 小時。
也就是說，就算真的設錯，只要在一兩天內發現並改回來，**積壓的信會自己送達**。
真正會遺失信件的是「指到一台會收下信的錯誤主機」——
而我們是逐筆照抄原值，不會發生這種情況。

**五、切換前可以先驗證。**
Cloudflare 會給兩組名稱伺服器。在還沒切換之前，就能用
<https://www.digwebinterface.com/>（可指定要問哪一台 DNS 伺服器）
直接向那兩台查詢，把答案跟 TWNIC 現有的逐筆比對。
**比對一致再切換**，等於先彩排一次。
