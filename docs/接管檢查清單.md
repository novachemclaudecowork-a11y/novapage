## 二、DNS 管理權 ⚠️ 唯一待處理項目（但可單方面解決）

### 關鍵觀念（請務必理解這一點）

DNS 有兩層，很多人會搞混：

```
第一層：網域註冊商（Registrar）  ← 貴公司握有 ✅
          ↓ 在這裡設定「要用誰家的 Name Server」
第二層：Name Server（DNS 代管）  ← 目前可能在設計公司手上 ⚠️
          ↓ 實際存放 A / MX / CNAME 等紀錄
```

**因為貴公司控制第一層，所以可以隨時把第二層換掉，不需要設計公司同意。**

這就是為什麼「網域自己註冊」如此重要 —— 它讓你永遠保有退路。

> ✅ **2026-11-16 已查明：DNS 不在設計公司手上。**
> 名稱伺服器是 `ns11/ns12.twnic.net.tw`（台灣網路資訊中心），
> 隨 `.tw` 網域註冊附帶的 DNS 代管——也就是說這一層本來就跟著公司的網域走。
> 已查到的完整紀錄見 [DNS現況.md](DNS現況.md)。
>
> 這代表接管 DNS **不需要設計公司配合**。下面的步驟仍然適用，
> 但目的從「取回控制權」變成「技術上的需要」（Workers 要掛自有網域，
> 名稱伺服器必須指向 Cloudflare）。

### 怎麼確認現況

登入網域註冊商的管理後台，找「**名稱伺服器**／**Name Server**／**DNS 設定**」：

- 如果顯示的是註冊商自己的（例如 `dns1.hinet.net`）→ DNS 在貴公司這邊，完全沒問題
- 如果顯示的是陌生的網址（例如 `ns1.某設計公司.com.tw`）→ DNS 目前由設計公司代管

### DNS 紀錄有哪幾種，各管什麼

把 DNS 想成一本**電話簿**：網域是公司名稱，電話簿裡登記著「找這間公司的各種事，分別要打到哪裡」。
不同的事查不同的欄位：

| 紀錄類型 | 管什麼 | 弄丟或抄錯的後果 |
| --- | --- | --- |
| **A**（或 AAAA） | 網址 → 網站主機的 IP 位址 | 網站打不開 |
| **CNAME** | 某個子網域 → 另一個名字 | 該子網域失效 |
| **MX** | **信要送到哪一台郵件主機** | **寄到本網域的信全部收不到** |
| **TXT** | 各種驗證字串（SPF、DKIM、DMARC、網域所有權驗證） | 寄出去的信被判定為垃圾信 |
| **NS** | 這本電話簿由誰保管 | 就是要換的那一層 |

### MX 是什麼，為什麼特別強調

**MX＝Mail eXchanger，郵件交換紀錄。** 它回答一個問題：
「有人寄信到 `@novananoinks.com.tw`，這封信要交給哪一台主機？」

關鍵在於，**同一個網域同時被兩件不相干的事情使用**：

```
novananoinks.com.tw
  ├─ 網站 www.novananoinks.com.tw  → 看 A 紀錄  → 網站主機
  └─ 信箱 ○○○@novananoinks.com.tw → 看 MX 紀錄 → 郵件主機
```

這兩條路**完全獨立**。所以搬 DNS 時若只顧著把網站的 A 紀錄抄過去、漏掉 MX，
結果會是：**網站一切正常，但從那一刻起全公司收不到信**。

更麻煩的是這種故障很安靜——網站看起來好好的，對方寄信也不一定馬上收到退信，
往往是幾天後才發現「怎麼都沒人回信」。這是搬 DNS 最常見也最痛的事故。

> ✅ **以貴公司的情況，這個風險其實很低。**
> 公司信箱是 `novachem@ms24.hinet.net`，那是**中華電信 HiNet 的信箱**，
> 不是 `@novananoinks.com.tw` 結尾的自有網域信箱。
> 也就是說，這個網域很可能根本沒在收信、沒有 MX 紀錄要保。
>
> **但還是要先查過再動手**——萬一設計公司當初有設 `info@` 或 `sales@`
> 之類的轉信，漏掉就出事了。查詢方法見下一節第 1 步。

### 建議做法：把 DNS 移到 Cloudflare（免費、一勞永逸）

**⚠️ 執行順序很重要，做反了會導致網站斷線或信件遺失。**

#### 第 1 步：查出現有的全部紀錄（絕對不能跳過）

到 <https://mxtoolbox.com/SuperTool.aspx>，輸入 `novananoinks.com.tw`，
依序查這幾項，**每一項都截圖存檔**：

| 在 MXToolbox 選 | 要看什麼 |
| --- | --- |
| `DNS Lookup` | NS 紀錄——現在是誰在代管（這就是設計公司那一層） |
| `MX Lookup` | **有沒有 MX 紀錄**。顯示「No records found」就代表這個網域沒在收信 |
| `A Lookup` | 網站主機的 IP（分別查 `novananoinks.com.tw` 與 `www.novananoinks.com.tw`） |
| `TXT Lookup` | 各種驗證字串，常被忽略 |
| `SPF Record Lookup` | 寄信驗證用，有的話要一起搬 |

也可以用 Google 的 <https://toolbox.googleapps.com/apps/dig/> 交叉比對一次。

**把截圖存成一個資料夾收好。** 這是萬一出錯時唯一的還原依據。

#### 第 2 步：確認網域註冊商的帳號能登入

`.com.tw` 通常是透過代理商（HiNet、PChome、Gandi 等）向 TWNIC 註冊。
先確認**登得進去**，而且找得到「**名稱伺服器 / Name Server / DNS 設定**」那一頁。

登不進去就先處理這件事——後面每一步都靠它。

#### 第 3 步：在 Cloudflare 加入網域（此時還不會生效）

1. 到 <https://dash.cloudflare.com/sign-up> 註冊免費帳號
2. Add a site → 輸入 `novananoinks.com.tw` → 選 **Free** 方案
3. Cloudflare 會自動掃描現有紀錄並匯入

**這個階段什麼都還沒改變。** Cloudflare 上的設定要等第 5 步改了 Name Server 才會生效，
所以可以慢慢核對，不急。

#### 第 4 步：逐筆核對（最關鍵的一步）

拿第 1 步的截圖，和 Cloudflare 掃進來的清單**一筆一筆比對**：

- [ ] A 紀錄的 IP 完全一致
- [ ] **MX 紀錄的主機名稱與優先權（Priority）數字完全一致**
- [ ] TXT 紀錄一字不差（**自動掃描最常漏掉這一項，要特別檢查**）
- [ ] CNAME 紀錄都在

有漏的就手動補上。**不確定的紀錄一律照抄，不要自作主張刪除**——
看不懂用途的紀錄往往正是某個服務在用的。

#### 第 5 步：改 Name Server

Cloudflare 會給你兩組像 `xxx.ns.cloudflare.com` 的網址。
到第 2 步那個註冊商後台，把名稱伺服器改成這兩組。

#### 第 6 步：等生效

通常幾小時，最長 48 小時。這段期間新舊兩邊**並存**——
有些人問到舊的、有些人問到新的，所以第 4 步的紀錄一致才不會時好時壞。

#### 第 7 步：驗證

- [ ] `www.novananoinks.com.tw` 打得開，內容和以前一樣
- [ ] **用外部信箱（Gmail 之類）寄一封信到公司信箱，確認收得到**
- [ ] 從公司信箱寄一封出去，確認沒有進對方的垃圾信匣

#### 第 8 步（獨立作業，建議隔幾天再做）：把網站指向新站

**不要和搬 DNS 同時做。** 一次只改一件事，出問題才知道是哪一關。

確認 DNS 搬家一切正常、信件正常收發幾天之後，再回到 Cloudflare
把 A／CNAME 指向新的 Workers 站台。那時就只是改一筆紀錄的事。

### 萬一出錯怎麼辦

名稱伺服器可以改回原本的，但一樣要等生效（數小時）。
**所以第 1 步的截圖才是真正的保險**——只要紀錄抄得完整，隨時可以還原。

完成後：**DNS 管理權 100% 回到公司手上，與任何廠商脫鉤，且往後免費。**

> 💡 這件事可以**現在就做**，不必等新網站完成。
> 只要紀錄搬得完整，網站與信件都不會受影響，使用者完全無感。
> 提前做好，將來新站要上線時就只是改一筆 A 紀錄的事。

## 五、切換上線時的注意事項

等新站做好、準備切換時：

1. **先在測試網址上完整驗收**（Cloudflare Pages 會提供免費預覽網址），不要直接動正式網域
2. **保留舊網址的轉址對照**
   舊站的 `view.asp?id=132&...` 這類網址 Google 已經收錄，
   新站須設定 **301 轉址**指向對應新網址，否則搜尋排名會掉。
   （重建時我會一併產出這份對照表）
3. **切換前再次確認 MX 紀錄無誤**，避免信箱中斷
4. **舊站先別急著關**，保留一至三個月作為備援與對照
5. 切換後到 Google Search Console 提交新的 sitemap

## 六、與設計公司的溝通建議

因為網域在貴公司手上，**談判地位其實很好**，不需要急，也不必起衝突。

建議**不要**一開始就談「交出原始碼」—— 依台灣《著作權法》第 12 條，
出資聘人完成的著作若未特別約定，著作權原則上歸受聘人，
這個要求容易陷入僵局，而且那些老舊的 ASP 程式碼**拿到也沒有用**。

比較有效的談法是就事論事：

> 「我們要進行公司網路資產的盤點，請提供目前 `novananoinks.com.tw` 的
>  完整 DNS 紀錄清單（A、MX、CNAME、TXT），以及網站上所使用的
>  產品照片原始檔。」

這是正當、具體的資產管理要求。

而且 —— 就算對方完全不配合也沒關係。DNS 紀錄可以自己用工具查出來，
產品照可以從網站上直接下載。**貴公司不需要對方的任何配合就能完成搬遷。**
